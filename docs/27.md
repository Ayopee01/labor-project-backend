### 27.10 Quick Filter จากการ์ด Summary หน้า Audit **(⚠️ Backend ยังไม่รองรับครบ)**
 
ปัจจุบันการ์ด Summary แสดงยอดรวมจาก `Summary` ก่อน pagination ได้ถูกต้องแล้ว แต่ `GET /api/admin/audit/events` รองรับตัวกรองเพียง `actor_type`, `event_type`, วันที่ และคำค้นหา จึงยังไม่สามารถเปิดให้การ์ดทุกใบกรองตารางได้อย่างถูกต้อง การกรอง `Data` ที่ Frontend หลัง pagination ห้ามใช้ เพราะจะกรองเพียงรายการในหน้าปัจจุบันและทำให้ total/summary/pagination ไม่ตรงกัน
 
Backend ต้องเพิ่ม optional query สำหรับ quick filter ดังนี้:
 
| การ์ด | Query ที่ต้องรองรับ | เงื่อนไข |
|---|---|---|
| รถที่เกี่ยวข้อง | `has_vehicle=true` | `VehicleJobId` ต้องไม่เป็น `null` |
| ทำงานอัตโนมัติ | ใช้ `actor_type=system` ที่มีอยู่แล้ว | ไม่ต้องเพิ่ม Backend |
| เหตุการณ์รวม | ไม่ส่ง quick filter | ใช้ filters จากแถบค้นหาตามเดิม |
| ต้องตรวจสอบ | `severity=critical` | ใช้กฎ severity กลางชุดเดียวกับ Summary/Frontend รวม `message_delivery_failed` |
| ดำเนินการโดยผู้ดูแล | ใช้ `actor_type=admin` ที่มีอยู่แล้ว | ไม่ต้องเพิ่ม Backend |
| มีเหตุผลประกอบ | `has_reason=true` | `ReasonCode` หรือ `ReasonText` ต้องมีค่าจริง |
 
ข้อกำหนดเพิ่มเติม:
 
1. Quick filter ต้องทำก่อนคำนวณ `Data`, `Pagination` และ `Summary`
2. Quick filter ต้องใช้ร่วมกับ `search`, `date_from`, `date_to`, `actor_type` และ `event_type` ได้
3. `severity` ต้องเป็น enum ที่ Backend validate และมี mapping กลางชัดเจน ห้ามให้ Frontend ส่งรายการ EventType จำนวนมากแทน
4. เมื่อ Backend รองรับแล้ว Frontend จึงเปิด interaction ของการ์ด และเมื่อเปลี่ยนการ์ดต้องกลับไปหน้า 1
5. เพิ่ม OpenAPI และ automated tests ว่า total, summary และข้อมูลทุกหน้าใช้ quick filter ชุดเดียวกัน

### 27.11 ชื่อแผงสำหรับ Vendor Actor ในหน้า Audit **(⚠️ Backend ยังไม่ส่ง)**
 
Event เช่น `vendor_rejected`, `vendor_confirmed` และ `vendor_rated` ส่ง `ActorType=vendor`, LINE `ActorId` และ `Metadata.boothCode` แล้ว แต่ยังไม่ส่งชื่อแผง ทำให้ Frontend แสดงได้เพียงรหัสแผงหรือ LINE UID ซึ่งตรวจสอบได้ยาก
 
Backend มีข้อมูล `GateTicket.boothName` อยู่แล้ว จึงไม่ต้องเพิ่ม table หรือ query รายแถวใหม่ ให้เพิ่ม field ต่อไปนี้ใน Metadata ของ Event ที่มี GateTicket:
 
```json
{
  "boothName": "ชื่อแผงค้า",
  "boothCode": "GV3/98"
}
```
 
ข้อกำหนด:
 
1. Frontend แสดง `boothName · boothCode` เป็นข้อมูลหลักของ Vendor actor
2. ถ้าไม่มี `boothName` ให้ fallback เป็น `boothCode`; ถ้าไม่มีทั้งคู่จึง fallback เป็น LINE `ActorId`
3. LINE UID ไม่ต้องแสดงเป็นข้อมูลหลักในตาราง แต่ต้องคง `ActorId` ใน API สำหรับตรวจสอบทางเทคนิค
4. เพิ่ม `boothName` ทั้ง Completion Submission event และ Ticket Rating event โดยใช้ relation `ticket.boothName` ที่ query อยู่แล้ว
5. ห้าม lookup API เพิ่มรายแถวจาก Frontend
 
### 27.12 System และ Security Audit ที่ Backend ยังไม่ได้บันทึก **(⚠️ Backend ยังไม่รองรับ)**
 
`GET /api/admin/audit/events` ปัจจุบันรวมข้อมูลจาก 8 durable sources ได้แก่ `VehicleJob`, `GateRequestLog`, `DriverSession`, `WorkerAssignmentEvent`, `TicketCompletionSubmission`, `TicketRating`, `MessageDeliveryLog` และ `AdminActionLog` จึงครอบคลุมหลัก ๆ เฉพาะงานรถ งานแรงงาน แผงค้า การแจ้งเตือน และ Admin action ใน operational flow เท่านั้น
 
`AdminActionLog` ปัจจุบันมี action type เฉพาะการจัดการงานรถ/แรงงาน เช่น override count, ยกเลิกงาน, ต่อเวลาสแกน, manual assignment และ force worker status ยังไม่ใช่ System Audit Log กลาง
 
Backend ยังไม่ได้บันทึกเหตุการณ์ต่อไปนี้เป็นประวัติแบบ append-only และ Audit API ยังไม่สามารถส่งให้ Frontend ได้:
 
| กลุ่ม | เหตุการณ์ที่ยังขาด | EventType ที่แนะนำ | ข้อมูลสำคัญ |
|---|---|---|---|
| Authentication | Login สำเร็จ | `auth_login_succeeded` | account, role, session reference, IP, user agent |
| Authentication | Login ไม่สำเร็จ รวม username ที่ไม่มีหรือรหัสผ่านผิด | `auth_login_failed` | attempted username แบบเหมาะสม, IP, user agent, failure code; ห้ามเก็บ password |
| Authentication | Logout | `auth_logout` | account, session reference, IP, logout source |
| Authentication | Force login และการ revoke session เดิม | `auth_force_login` / `auth_session_revoked` | actor/account, session/device reference และเหตุผล |
| Credential | ผู้ใช้เปลี่ยนรหัสผ่านตัวเอง | `account_password_changed` | account และจำนวน session ที่ถูก revoke; ห้ามเก็บรหัสผ่าน/hash |
| Credential | ผู้ดูแลรีเซ็ตรหัสผ่าน Admin หรือแรงงาน | `account_password_reset` | admin actor และ target account |
| Admin account | สร้างหรือแก้ไขบัญชีผู้ดูแล | `admin_account_created` / `admin_account_updated` | actor, target, before/after เฉพาะ field ที่เปลี่ยน |
| Admin account | เปลี่ยนระดับสิทธิ์, permission หรือสถานะบัญชี | `admin_permissions_changed` / `admin_status_changed` | actor, target, permission diff และ before/after |
| Worker account | สร้างหรือแก้ไขข้อมูลแรงงาน | `worker_account_created` / `worker_account_updated` | actor, worker code และ before/after เฉพาะ field ที่เปลี่ยน |
| System settings | แก้ runtime settings | `system_settings_updated` | actor และ before/after ของ key ที่เปลี่ยน |
| Gate Client | สร้าง/แก้ไข Client หรือเปลี่ยนสถานะ | `gate_client_created` / `gate_client_updated` | actor, client code และ changed fields |
| Gate Client | หมุน Secret | `gate_client_secret_rotated` | actor และ client code; ห้ามเก็บ secret เดิม/ใหม่ |
| Mobile App Version | เพิ่มหรือแก้ไขเวอร์ชัน/นโยบายบังคับอัปเดต | `mobile_app_version_created` / `mobile_app_version_updated` | actor, platform/version และ before/after |
| Own profile | แก้ข้อมูลโปรไฟล์หรือรูปผู้ดูแล | `admin_profile_updated` | actor และ changed fields; การเปลี่ยนภาษาอาจไม่ต้อง log เพื่อลด noise |
 
ข้อกำหนด Backend:
 
1. เพิ่ม System Audit storage แบบ append-only แยกจาก domain transaction ปัจจุบัน หรือขยายโครงสร้างกลางโดยไม่บังคับ `actor_account_id` สำหรับ login failed ที่หา account ไม่พบ
2. แต่ละ event ต้องมี `event_type`, `outcome`, `occurred_at`, actor/target reference, `request_id` หรือ `correlation_id` และข้อมูล IP/user agent เท่าที่นโยบายความเป็นส่วนตัวอนุญาต
3. Mutation ที่สำเร็จต้องเขียน Audit ใน transaction เดียวกับการเปลี่ยนข้อมูล เพื่อไม่ให้เกิดการเปลี่ยนข้อมูลสำเร็จแต่ไม่มี log; mutation ที่ rollback ต้องไม่เหลือ success log
4. `before` และ `after` เก็บเฉพาะ field ที่เปลี่ยน ไม่ต้อง snapshot ทั้ง record และต้องตัด password, password hash, access/refresh token, session token, LINE token, FCM token, Gate secret และข้อมูลลับทุกชนิด
5. Login failed ต้องบันทึกแบบไม่เปิดช่อง username enumeration ใน response และต้องมี retention/rate limit ที่เหมาะสม
6. เพิ่ม source ใหม่นี้เข้า `GET /api/admin/audit/events` ก่อน filter, summary และ pagination พร้อมรองรับ `actor_type`, `event_type`, date และ search แบบเดียวกับ event เดิม
7. เพิ่ม permission เฉพาะ เช่น `audit:read` สำหรับอ่าน System/Security Audit และกำหนดค่าเริ่มต้นตาม permission level; ไม่ควรผูกการอ่านข้อมูลความปลอดภัยไว้กับ `jobs:read` ระยะยาว
8. Frontend ต้องได้รับ stable event code และข้อมูลดิบที่ผ่านการ redact เท่านั้น การแปลชื่อเหตุการณ์และข้อความแสดงผลเป็นหน้าที่ Frontend
9. เพิ่ม OpenAPI และ automated tests สำหรับ success/failure, actor/target, transaction rollback, permission, redaction และ merged pagination
 
### 27.13 ความหมายของ Before / After และช่องว่างของ Event ปัจจุบัน **(⚠️ Backend ส่งเฉพาะ Metadata)**
 
- `Before` คือค่าของ field ที่เกี่ยวข้องก่อนดำเนินการ
- `After` คือค่าหลังดำเนินการสำเร็จ
- `Metadata` คือข้อมูลประกอบเพื่อระบุตัวเหตุการณ์ เช่น รหัสแรงงาน รหัสรถ action หรือ context อื่น ไม่ใช่ Before/After
 
Response type ของ `GET /api/admin/audit/events` ปัจจุบันมี `Metadata` แต่ยังไม่มี `Before` และ `After` ใน contract จริง แม้ Frontend รองรับสอง field นี้เป็น optional ไว้แล้ว ดังนั้น Drawer ต้องตั้งหัวข้อตาม payload ที่ได้รับ ห้ามแสดงข้อความว่า “ข้อมูลก่อนและหลัง” เมื่อมีเพียง Metadata
 
สำหรับ `worker_force_status_changed` Backend ปัจจุบันบันทึกเพียง `Metadata.status` ซึ่งเป็นสถานะเป้าหมาย/สถานะหลังดำเนินการ พร้อม `worker_account_id` และ `worker_code` แต่ไม่ได้บันทึกสถานะก่อนหน้า ทั้งที่ service อ่าน `queueEntry.status` ก่อนเปลี่ยนสถานะอยู่แล้ว
 
Contract ที่แนะนำสำหรับ event นี้:
 
```json
{
  "Before": { "status": "ready" },
  "After": { "status": "open_app" },
  "Metadata": {
    "workerCode": "MN00003"
  }
}
```
 
ข้อกำหนดเพิ่มเติม:
 
1. เก็บ Before/After ณ transaction หรือ operation ที่เกิดเหตุการณ์ ห้าม derive ย้อนหลังจากสถานะปัจจุบันหรือ `updatedAt`
2. Event ใหม่ในกลุ่ม System/Settings/Account ที่เป็น mutation ต้องส่ง Before/After ของ field ที่เปลี่ยนตามข้อ 27.12
3. Event operational เดิมที่ source ไม่มี Before/After ให้ส่งเฉพาะ Metadata ต่อไปได้และห้ามสร้างค่าปลอม
4. ระหว่างที่ Backend ยังไม่เพิ่ม field Frontend แสดงหัวข้อ “ข้อมูลประกอบเหตุการณ์”; ถ้ามีเฉพาะ Before หรือ After ให้หัวข้อตรงกับข้อมูลที่มี และแสดง “ข้อมูลก่อนและหลัง” เฉพาะเมื่อได้รับทั้งสองส่วนจริง
